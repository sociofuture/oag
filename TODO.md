## 1. `oneOf` / `anyOf` / `discriminator`

### Current behavior (checked)

| Spec | Java (`server/jax-rs`) | TypeScript (`client/typescript-fetch`) | Python (`server/python-*`) |
| --- | --- | --- | --- |
| A schema that is only `oneOf` / `anyOf` (no `properties`) | No model is generated. Every use becomes `Object` | No model. Every use becomes `any` | No model. Every use becomes `Any` |
| `oneOf` / `anyOf` used inline in a property | `Object` | `any` | `Any` |
| `properties` together with `oneOf` / `anyOf` | Only the properties are generated; **a warning is printed** | Only the properties are generated; no warning | Only the properties are generated; no warning |
| `discriminator` | Ignored | Ignored | Ignored |

Nothing fails, but the types are lost silently. That is the worst part of the current state.

### Work items

1. **Quick win: warn in every target.** Print the existing `oneof_unsupported` warning from TypeScript and Python too, and also for a schema that is only `oneOf` / `anyOf` (today only the Java target warns, and only for the "properties + oneOf" case).
2. **Get reference output.** The Java and TypeScript targets must match openapi-generator 7.12.0 exactly, but how it renders `oneOf` / `anyOf` / `discriminator` is not known here. Write a small spec (`oneOf` with and without a discriminator, `anyOf`, a property that is `oneOf`, a discriminator with a mapping), generate it with the real openapi-generator, and compare with `tools/cmp.mjs`. Do this before implementing the Java and TypeScript parts.
3. **Python** (own design, so no reference needed). Planned mapping with pydantic v2:
   - `oneOf` / `anyOf` → a union type (`A | B`) for the model, request body, response and property.
   - With a `discriminator` → `Annotated[A | B, Field(discriminator="kind")]`, using `mapping` where given.
   - Without a discriminator → pydantic's default smart-mode union. `oneOf` ("exactly one") may need a check that exactly one member matched.
   - The ABC annotations and `router.py` use the same union type.
4. **TypeScript** (once the reference is known). Expected shape: `export type Animal = Cat | Dog;`, with `AnimalFromJSON` / `AnimalToJSON` choosing the member through the discriminator or `instanceOf...` checks.
5. **Java** (once the reference is known). Expected shape: an interface or abstract class for the `oneOf` schema, `@JsonTypeInfo` / `@JsonSubTypes` for the discriminator, and the members implementing it.
6. **`allOf` with a `discriminator`.** Today `allOf` is always flattened. openapi-generator uses inheritance (`extends`) when a discriminator is present; check what the reference output looks like.

Done when: the sample spec generates without the warning for the supported cases, the Java and TypeScript output matches openapi-generator, and the Python targets accept and return each union member in the request tests.

## 2. Confirm more features against openapi-generator

The match with openapi-generator is confirmed only for the features used by the business spec (POST with a JSON body, no parameters, no enums). These are implemented but **unverified**; each needs reference output:

- path / query / header / cookie parameters (Java and TypeScript)
- enums (top-level and inline) and their naming
- `description` / `summary` / `notes` in Javadoc and JSDoc
- `useSwaggerAnnotations=true`, `interfaceOnly=false`, `useTags=true`, `dateLibrary=legacy`, `useJakartaEe=false`
- `apiKey` / `basic` authentication in `typescript-fetch`
- form bodies and file upload (`multipart/form-data`)
- `readOnly` / `writeOnly`, `format: password`, `uniqueItems` (Set), free-form objects, `additionalProperties`

A single "everything" petstore-like spec, generated by openapi-generator and kept in the repository, would cover most of this and could become the regression test (see 4).

## 3. Input handling

- `$ref` to an external file (`other.yaml#/components/...`). Needs a bundling step, or resolving the file relative to the spec.
- Swagger 2.0 input (convert to OpenAPI 3, or print a clearer hint).
- Vendor extensions (`x-...`) are ignored, except `x-codegen-request-body-name` in Java.

## 4. Tests and CI

- `npm test` is still a placeholder. Add regression tests that generate the sample spec for every target and compare with committed expected output (this needs a public spec and reference output; the business spec cannot be committed).
- The Python request tests (FastAPI / Flask / Falcon with a hand-written `_impl`) currently live outside the repository. Move them in, with a requirements file for the test run.
- `--check` mode: generate into a temporary directory and fail if it differs from the committed files. It enforces "generated files are never edited by hand" in CI.

## 5. Python servers

- Comments, docstrings and error messages inside the generated files are in Japanese and do not follow `--lang` (to keep the output the same on every machine). Make English the default and add an explicit option such as `-p comments=ja`.
- Authentication does not distinguish `security` schemes. Possible design: a verifier per scheme (`verify_<scheme>`), chosen from the operation's `security`, and support for OR / AND of requirements.
- Falcon: `multipart/form-data` file upload is not supported (the parameter receives `None`).
- Flask: a file parameter is the raw `request.files` value, not a typed object.
- Optional snake_case field names for the models (with aliases), instead of the JSON names.
- Optional separate command that creates missing `_impl` skeleton files once (never overwriting). It must stay outside `generate`, to keep the "generated files are never edited" rule.
